Fixed
A factory cell no longer loses Claude Code lines from its pages when the sessions database fails a write (TR-1665). Before, the lines were acknowledged and never reached the pages once the one-time move of sessions had finished. Now a delivery is answered with 503 while the sessions database takes no writes, so the Claude Code plugin sends the same lines again. A line the sessions database will not take is acknowledged, its session is marked incomplete, and a background repair copies the session's lines, counts and activity over from the event database. That repair runs at start and then every ten minutes, once the move has finished. A line that can never be stored is left out once, the daemon says so, and the lines behind it are not held up. The station page shows the newest lines that can be read when some cannot.

What a factory cell still does not recover: the one-off lines the plugin sends without retrying (the challenger's own timeline line, the end of a session, status line readings) are lost from the timeline if they arrive while the sessions database takes no writes, though a challenger result is still recorded. The marks that say token usage and challenger results were already filled live in the sessions database, so restoring or replacing the event database file does not run those fills again, and replies that an older version received between two starts are not counted again. A challenger result lost to a crash is not copied again.
